# Discover (planned for v0.4)

**Status: a plan, not a build step.** Discover is on the "Not in v0.1" list in `CLAUDE.md`. Nothing here is built before v0.4. This file records what the owner asked for on 2026-09-30, so the v0.4 brief can start from it.

## What it does

Discover finds songs you don't have yet, based on songs you do have. It shows them as a grid of cards. Each card can be played straight away in the app or downloaded into the library through the normal queue.

## 1. Where the picks start from (the "seeds")

The owner picks one or more of these:

| Seed | Example | Needs |
|---|---|---|
| A playlist | "Road Trip": give me 50 more like it | playlists (see "Depends on") |
| The whole library | 100 songs based on everything I have | the index (v0.1) |
| Most played | songs like the ones I play most | play history (v0.2) |
| Most listened-to artist | more like my top artist | play history (v0.2) |
| A named artist, plus similar bands | Linkin Park and close bands that sound like them | YouTube Music's related artists |
| One or more genres | hip hop | YouTube Music's genre and mood lists |
| Just recommend | no filter, a mix from the library | the index |

Seeds can be combined, e.g. "Road Trip" limited to rock, or two artists together.

## 2. How many

Presets: **10, 50, 100, 500**, plus a box to type any number (the owner's own example was 250).

## 3. How picks are found and ranked

- **Candidate lists from YouTube Music:** the radio for each seed song, "related" songs, an artist's "Fans might also like", and the genre and mood playlists. Last.fm "similar tracks" is the backup (the roadmap already says so). It needs an API key, which lives in the config folder, never in the repo.
- **Ranking:** a song that turns up for many seeds ranks higher than one that turns up once. Songs by artists the owner already has a lot of get a boost ("artist preference").
- **Never suggest:**
  - a song already in the library (checked with the matcher's normalize and match rules, not by title alone)
  - a candidate the owner rejected in review (`state.json` keeps these)
  - a song already in the download queue
  - the same song twice, e.g. two uploads of one track. The official YouTube Music version wins.
- **A one-line "why" on each card**, e.g. "On the radio for 4 songs in Road Trip" or "You have 31 Linkin Park songs".
- **Check the APIs first:** before relying on any ytmusicapi field named here (radio, related, related artists, moods and genres), check it against the installed version and record fixtures, as `CLAUDE.md` requires.

## 4. The results grid

**Playing inside the app is the main way to listen** (owner, 2026-09-30). Everything else on a card is secondary.

One card per song:
- artwork, title, artist, length and the "why" line
- **Play**: the big, obvious button. It plays inside the app from YouTube. Nothing is saved and nothing is written to the library.
- **Download**: adds the song to the download queue
- **A small row of platform logos** next to the song: **Spotify, Apple Music, SoundCloud** and one more (to be chosen, see the open questions). Each logo is just a link that opens a search for that song on that site, e.g. `open.spotify.com/search/<artist title>`. No login and no API key, so no secrets are involved.
- A checkbox for picking several songs, then **Download selected**.

## 5. Downloading

Discover never downloads anything itself. It adds jobs to the throttled queue from step 09a, so every rule still applies:
- format 140 only, with no fallback; a song without it goes to review
- the fingerprint gate
- verified tag writes
- journaled and undoable
- the daily cap

A download of many songs is a batch, so it shows the plan first (the list and the time estimate) and the owner confirms it before anything is queued.

**Time estimate:** worked out from the queue's own settings (the pause between downloads, the quiet start and the daily cap), not a fixed guess. Roughly:
- **250 songs:** about 2–3 hours
- **More than the daily cap (300 per 24 h):** split across days, with the day and time it resumes stated up front, e.g. "300 today, the other 200 from 3:10am tomorrow".

## 6. Guided mode

A short back-and-forth for when the owner doesn't want to set filters:

> **App:** What music would you like today?
> **Owner:** Hip hop
> **App:** Would you like to just play it, or download it?
> **Owner:** Download it
> **App:** How many songs?
> **Owner:** 250
> **App:** Downloading 250 hip hop songs, weighted towards the artists you listen to most and skipping anything you already have. This will take about 2–3 hours, paced so YouTube doesn't block us. *[Start]*

Guided mode is only a front end for the same seeds, counts and plan as the grid. It adds no logic of its own. "Just play it" makes a temporary play queue from the picks and saves nothing.

## 7. Engine and app split

- **Engine:** RPC methods along the lines of `discover.suggest` (seeds, filters and count in; ranked picks with "why" lines and an estimate out) and `discover.enqueue` (picked ids in; queue jobs out). All YouTube calls go through `musicorg.youtube` and its rate limiter, including the lookups for in-app playback.
- **Mac app:** the grid, the player and guided mode.
- Any new state, decision or tag value (for example a provenance value marking a song as found by Discover) is added to "Enums" in `ENGINE_API.md` first.

## Depends on

- **Playlists (v0.2):** these don't exist in the library contract yet. Following the "files are the source of truth" rule, they would likely be `.m3u8` files in a managed `Playlists/` folder. This has to be decided in the contract before Discover can use a playlist as a seed.
- **Play history (v0.2):** kept in `state.json`, per the library contract, section 5. "Most played" and "most listened-to artist" need it.
- **The in-app player (v0.2)**, for Play.

## 8. Where Discover downloads go

The owner wants Discover songs kept apart from the main library, grouped by genre and by when they were downloaded. Their sketch: `Local Files → Discovered → Rap → January`.

**Proposal (to confirm at v0.4):**

```
<LibraryRoot>/
  Music/                               the main library, unchanged
  Discovered/                          a new managed folder, next to Music/
    Rap/
      2026-01 January/
        <Artist> - <Title>.m4a
        <Artist> - <Title>.lrc
    Indie/
      2026-01 January/
```

- **A folder next to `Music/`, not inside it.** Inside `Music/` it would clash with an artist who happens to be called "Discovered". The app shows it as "Local Files → Discovered".
- **The month includes the year and a number** (`2026-01 January`). With plain "January", January 2026 and January 2027 would land in one folder, and the months would sort alphabetically (April, August, December …) instead of in order.
- **One broad genre per folder**, from a short fixed list (about a dozen: Rap, R&B, Pop, Rock, Indie, Electronic, Metal, Country, Jazz, Classical, Latin, Other). YouTube Music's finer genres ("Alternative Hip Hop", "Trap") map onto these, and the full genre is still written in the file's genre tag. Without a short list the folder count grows without end.
- **Files stay the source of truth.** A new tag records the download date and the folder genre (added to "Enums" and the contract first). The folders can then be rebuilt from the tags, like everything else.
- **Discovered works as an inbox.** Two actions on a song:
  - **Keep**: moves it into the main `Music/<Artist>/<Album>` layout (journaled and undoable).
  - **Remove**: sends it to the Trash.
  - A whole month can be cleared in one go, e.g. "remove everything in Rap → 2026-01 January that I never played". It's undoable, like every batch.
- **Duplicate checks cover both folders.** A song in `Discovered/` counts as owned, so it's never suggested or downloaded twice.

This changes the library contract (a new managed folder, new naming rules and a new tag), so the contract is updated first, as for any change.
